# Decisions

One line each: date — decision — reason. Append only.

- 2026-09-28 — Use the hosted Neon Postgres from `.env` (DATABASE_URL / TEST_DATABASE_URL) instead of Docker Compose Postgres — owner's instruction for this run overrides Spec §2 / Rule 4/9; no docker-compose.yml is shipped yet.
- 2026-09-28 — Prisma 7.10.0 (latest stable) rather than the npm `latest` tag (8.0.0-rc.17) — the `latest` tag points at a release candidate.
- 2026-09-28 — Prisma 7 layout: `prisma.config.ts`, `prisma-client` generator output in `src/generated/prisma` (git-ignored, regenerated on `postinstall`), `@prisma/adapter-pg` driver adapter — required by Prisma 7.
- 2026-09-28 — Migrations read `MIGRATE_DATABASE_URL` if set, else `DATABASE_URL` — Neon's pooled URL works for migrate today, but providers differ.
- 2026-09-28 — Auth: Better Auth 1.7 (email/password + magic-link plugin); Auth.js fallback not needed — Spec §2 first choice worked.
- 2026-09-28 — Public sign-up disabled for both password and magic link; accounts are created only from invitations (seeded users are created directly with Better Auth's `hashPassword`) — Spec §4 "no passwords are ever shared" / invitation-only onboarding.
- 2026-09-28 — Magic-link tokens stored hashed, 15-minute expiry, single use — Spec §4 token hygiene applied to sign-in links too.
- 2026-09-28 — Better Auth's built-in rate limiter uses in-memory storage (10/min password, 5/min magic link); app-level limits (invitations, exports, PIN) use a Postgres fixed-window table `RateLimit` — memory store is fine for a single Node instance; switch Better Auth to `storage: "database"` if deployed multi-instance.
- 2026-09-28 — Every tenant-owned table carries `businessId` directly (denormalised) — lets the data-access layer enforce isolation with one uniform rule instead of per-model join logic.
- 2026-09-28 — Data-access layer is a Prisma client extension `tenantDb(businessId)`: ANDs `businessId` into every where, stamps it on creates, verifies every `*Id` reference points into the same business, refuses nested relation writes, restricts `User` to members and forbids traversing user→other memberships/sessions/accounts, and blocks auth tables — isolation enforced in one place and proven by `tests/integration/tenant-isolation.test.ts`; a unit test keeps its model lists in sync with the schema.
- 2026-09-28 — Only `src/server/{db,auth,platform,email}`, `audit.ts`, `rate-limit.ts` and `/dev` may import the raw Prisma client (ESLint `no-restricted-imports`) — makes bypassing the tenant layer a lint error.
- 2026-09-28 — Raw SQL (`$queryRaw`) is not intercepted by the tenant extension; it is only used in whitelisted server modules — Prisma extensions cannot scope raw SQL.
- 2026-09-28 — Business is selected by URL (`/b/[businessId]/…`), not by a cookie — two tabs on two businesses can never post an action to the wrong business.
- 2026-09-28 — A non-member requesting `/b/<id>` gets 404, never 403 — a 403 would confirm the business exists (Spec §7.1 isolation).
- 2026-09-28 — Money stored as integer cents (`Wage.rateCents`; salary = cents per year); multipliers/percentages as Decimal — avoids float rounding in pay calculation.
- 2026-09-28 — `Business.workDayStart` stored as `workDayStartMinutes` (default 240 = 04:00 local) — integer minutes are unambiguous and easy to test.
- 2026-09-28 — Overtime/min-daily-pay/split-shift/holiday-eligibility settings live on a 1:1 `PayRules` table; `vacationPayPercent`, `workDayStartMinutes`, `burdenPercent` stay on `Business` as the spec names them — keeps the Pay rules screen backed by one row.
- 2026-09-28 — Added tables beyond §13: `RateLimit`, `PinAttempt` (PIN attempt log, §7.1), `ScheduleConflict` (§6.4 dashboard items), `PayRules` — each backs an explicit spec requirement.
- 2026-09-28 — Default permission sets: Owner all; General Manager all except `roles.manage`/`payrules.manage`; Manager people/schedule/approvals/time/timesheets/reports/broadcast; Assistant Manager schedule/approvals/time edits/broadcast; Shift Lead `trades.approve`; Employee none — spec gives role names but not their default permissions; owner can change all of them.
- 2026-09-28 — Province presets (`src/lib/pay-presets.ts`) for CA-ON, CA-BC, CA-AB, CA-QC, US-CA, US baseline, generic; seeded unconfirmed — spec requires presets but not their values; owner must confirm them on Pay rules, the app never claims compliance.
- 2026-09-28 — Product name "Shiftwise" in UI/email copy — spec names no product; one string in `messages/en.json` to change.
- 2026-09-28 — i18n with next-intl "without i18n routing": locale from a `locale` cookie, English complete, fr-CA/ja catalogues fall back to English key-by-key — Spec asks for structure ready for fr-CA/ja, not locale-prefixed URLs.
- 2026-09-28 — System font stack instead of `next/font/google` — no network fetch at build time (Spec rule 4: no external services required).
- 2026-09-28 — shadcn/ui (base-nova style) with button/input/select/tab heights raised to 44px on mobile (`h-11 md:h-9`) — Spec §11 touch targets ≥ 44 px.
- 2026-09-28 — Next.js dev indicator disabled — it overlaps the mobile bottom tab bar and intercepts taps.
- 2026-09-28 — Missing `BETTER_AUTH_SECRET` / `PIN_HMAC_SECRET` fall back to fixed insecure placeholders in development and throw in production — the provided `.env` only has database URLs; dev must still run.
- 2026-09-28 — Integration + e2e tests run against `TEST_DATABASE_URL`; e2e global setup re-seeds it (TRUNCATE); integration tests create uniquely-named businesses and never truncate — safe to run repeatedly against a shared remote DB.
- 2026-09-28 — Prisma interactive transactions: maxWait 15 s / timeout 30 s — remote Neon connections can take several seconds to start a transaction after idling.
- 2026-09-28 — Invitation acceptance lives in the platform layer (`src/server/platform/accept-invitation.ts`) using the raw client constrained to the invitation's businessId — the visitor has no membership yet, so no tenant context exists.
- 2026-09-28 — "Continue with magic link" on an invitation creates the account (no password) and accepts, then emails a sign-in link — Better Auth has no public API to mint a session server-side; this keeps sign-in on the normal, audited path.
- 2026-09-28 — An existing user accepting an invitation must sign in first (sign-in supports a same-origin `?next=`) — the invitation link alone doesn't authenticate an existing account.
- 2026-09-28 — Only an Owner may invite/assign the Owner role; everyone else only roles strictly junior to their own — §3.3 rank rule applied to invitations and role changes.
- 2026-09-28 — A non-owner holding `roles.manage` may only manage roles junior to their own and only grant/revoke permissions they hold themselves — prevents privilege escalation through role editing.
- 2026-09-28 — The "unaccepted after 72 h" warning measures from `Invitation.sentAt`, which resets on resend — a freshly resent invitation shouldn't warn immediately.
- 2026-09-28 — A late `delivered` webhook never overrides a recorded `bounced`/`complained` for the same email — an invitation must never sit on "Invited" when the email never arrived.
- 2026-09-28 — Resend webhook verified with a Web-Crypto Svix implementation; endpoint returns 503 when `RESEND_WEBHOOK_SECRET` is unset. Dev emails page has "Simulate delivered/bounced/complained" buttons so the bounce flow is testable without Resend.
- 2026-09-28 — PIN change re-auth: current password, or a session created < 10 minutes ago (i.e. just signed in via magic link) — §7.1 "password or magic-link re-auth".
- 2026-09-28 — Manager "Reset PIN" clears the PIN; the employee is gated to a Set PIN screen on next visit — the manager never chooses or sees a PIN.
- 2026-09-28 — Deactivation deletes the user's sessions only if they have no other active membership — sessions are per user; access to this business is already cut by `accessRevokedAt`, and a job elsewhere must keep working.
- 2026-09-28 — Optional profile photo deferred to Phase 8, where the file-storage interface (local dev / S3 prod) is built for message attachments — avoids building storage twice.
- 2026-09-28 — Setup wizard collects all four steps client-side and saves once at the end; map-pin picking is deferred to Phase 3 (lat/lng inputs + "Use my current position" for now) — Phase 3 owns the geofence picker.
- 2026-09-28 — Onboarding gates in the app layout: profile incomplete → profile; PIN cleared → set PIN; Owner with setup incomplete → wizard. Non-owners are not blocked by an unfinished setup.
- 2026-09-28 — Native `<select>` used for form dropdowns (NativeSelect) instead of the shadcn popover Select — OS pickers on phones, better accessibility, reliable to test.
- 2026-09-28 — Pay uses the wage in force on the pay period's first day (`wageForPeriod`); Scheduled-wages estimates use the wage in force on the shift's date (`wageOn`) — §8 "a raise dated mid-period must leave the current period at the old rate throughout"; schedules are labelled estimates.
- 2026-09-28 — A position-specific wage beats the general wage for that position, regardless of which is newer — simple, predictable rule; the spec gives per-position wages without a precedence rule.
- 2026-09-28 — Wage history is append-only; a new wage may not take effect on or before the end of an approved pay period — "changing a wage never rewrites past timesheets".
- 2026-09-28 — Nobody may set their own wage except an Owner; others need `wages.edit` and must outrank the person — mirrors the self-edit rule for time entries; the spec is silent on self-wage edits.
- 2026-09-28 — Salary wages cannot be tied to a position — a salary is per person, and salaried staff are excluded from overtime (§8).
- 2026-09-28 — Geofence map picker uses Leaflet with OpenStreetMap tiles (`NEXT_PUBLIC_MAP_TILE_URL` to override); lat/lng inputs and "Use my current position" work without tiles — progressive enhancement keeps Rule 4 (no external service *required*).
- 2026-09-28 — "Test geofence" recommends radius = ceil((max(distance + accuracy) × 1.1) / 10) × 10, clamped 25–1000 m; with no centre set, the mean reading becomes the centre — the spec asks for a recommendation from ten readings but not the formula; this contains every observed reading including its uncertainty.
- 2026-09-28 — Business settings split into three saves on one page (business info, request rules, time clock rules); `workDayStart` is edited there too — §10 settings list; Pay rules gets its own screen in Phase 7 (§7.6.8).
- 2026-09-28 — Rounding intervals limited to 1, 5, 6, 10, 15 minutes; interval stored as 0 when rounding is off — common payroll intervals; avoids a stale interval being applied later.
- 2026-09-28 — Scheduling warnings are computed on read (not stored): every view recomputes them from current data, so they stay visible everywhere until the cause is resolved, and are hidden once the shift has ended — satisfies "persistent, not momentary" (§5.1) without stale stored warnings.
- 2026-09-28 — Minimum rest between shifts for the SHORT_REST warning is 8 h (constant `DEFAULT_MIN_REST_HOURS`); two shifts on the same local day are a split shift, not a rest problem — spec lists the warning but no threshold.
- 2026-09-28 — Overtime-risk warnings use scheduled hours after planned unpaid breaks, per local day and per Monday-start week, against the PayRules daily/weekly thresholds — a planning estimate; pay itself uses punches (§7.6.3).
- 2026-09-28 — Availability warnings check the shift's start day only, using the newest approved availability set effective on that date — overnight shifts are judged by the day they start, matching the work-day rule (§7.6.1).
- 2026-09-28 — Scheduled wages = scheduled hours after planned unpaid breaks × hourly wage in force on the shift date (position-specific first); salaried staff excluded; shifts with no wage on file are counted and shown — labelled "Scheduled wages", loaded cost only when burden % is set (§5.3).
- 2026-09-28 — Editing a published shift applies immediately (staff see the new time) and queues a notification; drafts are invisible to staff until "Publish" — simplest model matching "editing a published shift notifies the affected employee".
- 2026-09-28 — Notification batching: one pending entry per employee per week (`batchKey`), which stores what that employee last saw of each shift the first time it changes; each change pushes `flushAfter` 10 minutes out; the flush diffs before → after and drops the message if everything was changed back — §9.1 one message per person, with diffs, only for people whose shifts changed.
- 2026-09-28 — Due notifications are flushed in-process every 60 s (`src/instrumentation.ts`) and optionally by `POST /api/cron/notifications` with `CRON_SECRET` — no extra infrastructure (§2); email is skipped if the person opted out of that type.
- 2026-09-28 — Deleting a draft shift hard-deletes it; deleting a published shift soft-deletes it (`deletedAt`) so the removal can be notified and audited.
- 2026-09-28 — Copy previous week recreates each shift at the same local wall-clock times 7 days later (DST-correct), as drafts, skips exact duplicates, and leaves shifts of people who have since lost access open.
- 2026-09-28 — .ics feed is per user (not per membership) at `/api/calendar/<token>.ics`; token stored hashed in `CalendarFeed`, rotatable; contains only the user's own published shifts across their active businesses — §5.3 "feed per user"; no colleague data leaks.
- 2026-09-28 — Location switcher choice is saved on the membership (`preferredLocationId` / `preferAllLocations`) via a server action; `?loc=` in the URL overrides it for that view — "remembered per user between sessions" (§5.2) per business.
- 2026-09-28 — Weeks run Monday–Sunday in the location's timezone for the grid, overtime-risk and copy-week — common in Canadian hospitality; pay-period weeks come from the pay period anchor in Phase 7.
- 2026-09-28 — Seed data is relative to the current date (this week published, next week drafts) so a fresh seed always shows a live schedule; statutory holidays are seeded on fixed 2026 dates.
- 2026-09-28 — Eligibility (§6.0) treats an unknown date of birth as failing a position's minimum age — a minimum-age requirement can't be shown to be met without a DOB.
- 2026-09-28 — For a manager's direct assignment, the §6.0 predicate is shown in the shift editor as "not normally eligible" (position/location/access) alongside the §5.1 warnings, and never blocks — "a manager assigning deliberately is different from an employee swapping around a rule".
- 2026-09-28 — Drop model: a drop immediately offers the shift to eligible staff while the dropper stays assigned; with `dropNeedsApproval` off the shift becomes open at once. A claim on an offered shift needs approval if either the pickup or the drop setting requires it; a manager can also approve a drop with no taker (shift becomes open).
- 2026-09-28 — The one-active-claim partial unique index is on `(shiftId, claimGeneration)`; `Shift.claimGeneration` increments whenever a shift changes hands or becomes claimable — keeps "at most one pending-or-approved claim per shift" per round while allowing a shift that is later dropped again to be claimed again. Every transfer is a conditional update on `(membershipId, claimGeneration)`.
- 2026-09-28 — Swaps: coworker accepts first, then a manager approves (unless `swapNeedsApproval` is off, in which case acceptance completes it); the approver must outrank both people; eligibility is re-checked both ways at approval.
- 2026-09-28 — Time off: all-day requests use the requester's first location's timezone (else the business's); partial-day requests are within one day. Minimum notice does not apply to type "sick", and sick time may be recorded for past dates; other types must start today or later — the spec is silent, and requiring 14 days' notice for sickness would be absurd.
- 2026-09-28 — Approval re-checks blackout and minimum notice (notice measured from the submission date) — "self-approval skips the reviewer, never the rules"; a blackout added after submission blocks approval.
- 2026-09-28 — Escalation is computed on read (pending longer than `escalateAfterHours` while self-approval is off) and shown as an "Escalated" badge and dashboard count to every eligible approver — no background job needed.
- 2026-09-28 — Approvers see requests from people junior to them at their locations (all locations with `locations.scope_all`); requests go to every eligible approver as in-app notifications — there is no reporting-line hierarchy in the spec.
- 2026-09-28 — Availability submissions replace any still-pending submission; auto-approved (setting off) changes still run the §6.4 re-check.
- 2026-09-28 — §6.4 conflicts are stored in `ScheduleConflict` and auto-close ("superseded") when the shift is reassigned, deleted or ends; "Reassign" opens the schedule at that week/location, "Make open" unassigns (notifying the employee), "Keep anyway" closes it — all audited.
- 2026-09-28 — Request notifications (pending/approved/denied, swap proposals) are immediate in-app Notification rows; email delivery for them follows the Phase 8 preferences work.
- 2026-09-28 — `scripts/with-test-db.ts` sets `PRISMA_SCHEMA_DISABLE_ADVISORY_LOCK=1` — Neon's pooled connection stranded Prisma's session advisory lock (P1002); only one process ever migrates the test DB.
- 2026-09-28 — Geofence with no position: refused when the location's mode is `required`; accepted and flagged GEO_UNCERTAIN in `warn` mode — "punch refused when geofence is required"; warn mode shouldn't lose honest punches.
- 2026-09-28 — A shift's custom geofence override is enforced with the location's mode (off → warn) and always flags OFFSITE; override "off" accepts anywhere and flags OFFSITE — §7.2 offsite work.
- 2026-09-28 — Clock-in more than `earlyClockInMinutes` before a shift that starts within 12 h is refused ("too early") with the time it opens; otherwise with no shift it's unscheduled (flagged, or refused if disallowed). Offline punches skip the too-early rule (the time already happened).
- 2026-09-28 — LATE / EARLY_LEAVE use `lateToleranceMinutes` for both directions — one tolerance setting in §7.3.
- 2026-09-28 — Missing clock-out: flagged by a once-a-minute in-process sweep and on every clock/time-review view; the entry stays open forever until a human sets the time. The employee's answer is a CorrectionRequest; once answered they may clock in again while the old entry waits for a manager — §7.3 "cannot clock in again until it is answered".
- 2026-09-28 — A clock-out with no open entry (or only a stale one) creates a new entry with no clock-in, flagged MISSING_CLOCK_IN, and notifies time managers — §7.3 "the same applies in reverse".
- 2026-09-28 — Missing-punch flags are resolved only by entering the missing time (an audited edit); other flags are confirmed/acknowledged with a mandatory reason, also audited in TimeEntryAudit — §7.7 "explicit human resolution … recorded as a normal audited correction".
- 2026-09-28 — PIN attempts made while locked are logged but don't extend the lock.
- 2026-09-28 — Offline queue lives in the page (localStorage), not a service worker, and syncs on page load and the `online` event; personal offline punches are authenticated by the session at sync (the PIN can't be verified offline without shipping the HMAC secret) and are provisional (OFFLINE_QUEUED blocks approval until a manager confirms). The offline app shell/service worker comes in Phase 9 (PWA).
- 2026-09-28 — Kiosk: enrolling requires `timeclock.edit`; the device token is an httpOnly cookie valid 400 days; enrolment signs the manager out of that browser. After a correct PIN the kiosk gets a 90-second HMAC "ticket" so the chosen action doesn't need the PIN twice. Leaving kiosk mode needs the PIN of someone with `timeclock.edit` or `business.settings` and revokes the device. Kiosk punches record the kiosk's location.
- 2026-09-28 — `/clock` redirects to the business whose next shift starts soonest; the clock page shows a "Clocking for" switcher; `/me/hours` lists the user's own entries across businesses via the platform layer — managers never get a cross-business view.
- 2026-09-28 — Manager time edits and employee correction times are entered as local wall-clock values and converted on the server with the entry's LOCATION timezone (never the browser's) — an e2e run on a machine in another timezone caught the browser-timezone version producing a finish time before the clock-in.
- 2026-09-28 — BREAK_MISSED is raised in Phase 7a together with break rules (§7.6.3), keeping all pay-rule logic in one tested module.
- 2026-09-28 — `TimeEntry.location` relation added (FK) so entries can be listed with their location's name/timezone.
- 2026-09-28 — §7.6.1 read as: an entry's work-day is the local date of its clock-in, minus one day if the clock-in is before `workDayStart`; the pay period is the one containing that work-day (periods are whole work-days). Rule 3 says the single clock-in rule decides both, "the one the app uses everywhere". Flagged for review in PROGRESS.md because it makes a 01:00 Monday clock-in belong to the period containing Sunday.
- 2026-09-28 — Overtime weeks for weekly/bi-weekly periods are the 7-day blocks the period is made of (anchored on `payPeriodAnchorDate`, fallback Monday 2024-01-01) — a bi-weekly period is two such weeks by construction.
- 2026-09-28 — Pay arithmetic is in integer seconds and cents; each pay line (kind × rate × multiplier) is rounded once, half-up.
- 2026-09-28 — Pay uses rounded punch times when rounding is enabled (raw times kept on the entry); worked time = real elapsed time between instants (DST-correct) minus actual unpaid break punches, breaks clipped to the entry, an open break ending at clock-out.
- 2026-09-28 — BreakRule reading: work may not run longer than N consecutive hours without a break of at least M minutes; shorter breaks don't reset the count; exactly N hours is fine. BREAK_MISSED is raised at clock-out and after edits; resolution is explicit: "taken, add it" (adds a break via an audited edit) or "missed, pay it" (flag resolved, time stays paid).
- 2026-09-28 — Holiday premium (worked) = hours on the holiday's work-day × rate × premiumMultiplier, added to normal pay, and does not depend on eligibility ("worked the holiday → premium"; eligibility is attached to the not-worked amount). Holiday pay uses the wage in force at the start of the period containing each lookback day, straight time only.
- 2026-09-28 — The "average day's pay" divisor is owner configuration (`PayRules.holidayAverageDivisor`: days worked, or a fixed number), null by default so it is never guessed; CA-ON preset = fixed 20 over 28 days, CA-BC preset = days worked over 30 days; other presets leave it unset.
- 2026-09-28 — Minimum daily pay tops a work-day with any payable time up to the minimum at that day's first rate; top-up hours are not worked hours and never count toward overtime.
- 2026-09-28 — Vacation accrual = round(gross × vacationPayPercent / 100) where gross includes every earnings line of the timesheet (regular, overtime, top-ups, holiday premium and holiday pay) — §7.6.5 "grossWages × percent".
- 2026-09-28 — Salaried pay per period = annual salary ÷ periods per year (52/26/24/12), no hourly calculation, no overtime (§8).
- 2026-09-28 — Where §7.6 is silent the calculator returns a `blocked` reason instead of a number, and such a timesheet can't be approved even by an Owner with exceptions: weekly overtime under semi-monthly/monthly periods (`WEEK_UNDEFINED`), overtime in a week with more than one hourly rate (`MIXED_RATE_OVERTIME`), average day not configured, no wage on file. See PROGRESS.md "Blocked".
